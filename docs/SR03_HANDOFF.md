## Расширение 2×2 км для SR03

в физическом пространстве Unity; со всех сторон добавляется 500 м. Таблица ниже — обязательный контракт,
а не команда изменить географию в SR02.

Не масштабировать старые точки ×2. Все существующие design-точки сдвинуть +500, размеры/радиусы
и Y оставить прежними. Старые tile indices получают +2,+2; 16 старых становятся центральными 16 из 64.
World-space sampling должен сохранить phase/seed в ядре: перенос координат noise/ID входа на +500
без компенсации изменит гору, деревья и ресурсы даже при неизменном Unity положении.

### Изменения генерации по порядку

1. Ввести отдельный versioned definition для новых миров; прежний loader/snapshot adapter продолжает
   читать 1 км. Не переиспользовать старый generation ID для другой геометрии. Предлагаемое новое ID
   `serenity-world-map-sr-v3` окончательно фиксируется в SR03 вместе с save compatibility тестом.
2. Убрать конкретные 4/16/1000/1025 и фиксированную формулу только там, где они означают размер:
   `TiledWorldDefinitionLoader` (в т.ч. ValidateProjectionFormula/ParseTerrainContracts/ValidateTiles),
   height samplers, fog/scouting extents, камеры/minimap, placement spatial indexes, border/horizon,
   world warmup/progress, route caches и acceptance tests. Не заменять механически все числа 4/16.
3. Зафиксировать старый Unity seed-space и legacy identity frame в центральном квадрате.
   Stable keys не зависят от новых tile index/итерационного ordinal. Новые ресурсы имеют новый namespace.
   Если текущая формула ID включает generation, для ядра явно сохранить прежний identity-generation salt;
   новая версия геометрии не должна автоматически заменять этот salt у существующего ресурса.
   Нужна сверка baseline core IDs/stock/depletion до и после, плюс save/reload новых 2 км и старых 1 км.
   Старые слоты не удалять и не мигрировать без проверенной процедуры. Для SR03 допустим отдельный New Game
   generation с сохранённым чтением старой версии; автоматическое расширение старых сейвов не требуется.
4. Height field: 8×8×257; общая граница 2049; те же метры на sample. Геометрия горы и озера защищена
   неизменяемой маской. Дальние северо-восточные гряды ниже по видимому силуэту; не заслоняют ориентир.
5. Составить непрерывную гидрологию: верхняя река из I/L, старое ядро с мягкими меандрами,
   новое устье M/P и море O/P. В HTML центры четырёх озёр сохранены как безопасная база; остальные берега
   можно переработать. Проверить монотонный профиль уровня вдоль стока, соединения притоков, отсутствие
   висящих водных поверхностей. Путь/мост и wet/no-build меняются одним revision с руслом.
6. Biome/wetness/slope masks → покрытия → buildability/проходы → крупные лесные массы → ресурсы → детали.
   Полосы 35–70 м, без швов на административных полигонах A–P. Береговые террасы асимметричны;
   природные формы не повторяют строительную сетку 2 м. Ресурсы конечны, с прежней Production/Ecology authority.
7. Площадки I1…P1 в HTML — кандидаты, проверить dry slope/POI/ownership/путь. Не добавлять новые
   государства или бесплатные здания. S1/S2/S3 остаются действующими location IDs, новые площадки только география.
8. Пересчитать связный route graph. Существующие authored routes содержат геометрические приближения;
   нельзя считать любую нарисованную линию сухой. Новые R1–R4 задают каркас, X4 — новый переход у устья;
   для каждого пересечения фактической воды нужен отдельный crossing ID и физический мост/брод.
9. Только после недекорированного 64-tile замера принимать стратегию памяти. Сырые float heights:
   16×257²×4 ≈4,03 MiB → 64×257²×4 ≈16,13 MiB, **это не полная память Terrain/NavMesh/textures**.
   По умолчанию не возвращать runtime bake на пути камеры. При неприемлемой памяти/загрузке сначала
   кэш/пакетирование/снижение alpha/detail overhead, затем отдельное решение о resident view window.

Перенести прежние внешние scenic sea/ridges/horizon с границы центрального километра на новый внешний
периметр: нельзя оставлять декоративное море или backdrop поверх новой играбельной суши.
На схеме горный охранный эллипс совпадает с существующей `build_ridge_restricted` зоной и служит ориентиром,
а не доказанным пределом влияния всей горы. До правки заморозить высоты всего существующего региона C
и фактических alpine-масок, включая их заходы в соседние регионы; сравнить hash/sample grid и силуэт.
Геометрия и маска снега — отдельные каналы: разрешённая коррекция нижнего снега не разрешает изменить высоты.

### Лимиты 2 км и обход всех районов

Плановые caps: ≤12 000 интерактивных деревьев, ≤30 000 декоративных деревьев/кустов,
≤3000 интерактивных трав/кустов, ≤60 000 ground instances; active tree proxies ≤650 на первый замер.
Это верхние границы, не минимальная требуемая плотность. Высокий LOD и тени не растягивать на 2 км.
Камень/трава/листва не создают по-объектный tick. Плотность уходит в группы; поляны остаются свободными.

Маршрут обзорной камеры записан в `plan-data.json.camera`, D2; номера 1–16 включаются в HTML.
Порядок: A → B → C → G → M → P → O → E → F → H → D → L → I → J → K → N.
Для каждого района: общий вид, RTS, уровень жителя, день/вечер; отдельные проходы R1–R4 и внутренние
поперечные цепочки через все доступные границы тайлов. Полный SR04 должен составить матрицу 8×8,
отмечая intentional water/cliff как «непроходимо по замыслу», а не без проверки как PASS.

Снег: нижняя полоса 40–80 м, покрытие примерно 60→30→10→0%, низкочастотные пятна и учёт нормали;
верхние высоты/силуэт без изменений. Лёд: 0–3 крупных collider-free формы в защищённой части озера,
не заслоняющие обзор/рабочие подходы. M06: исключить всю болотную рыбу, включая пересечение траекторий;
канонический stock всей реки не удалять из-за малого болотного отрезка. У болотных landing candidates
нельзя оставлять действующий промысел; выбрать обычный берег того же источника или корректный отказ.
